TWO PROBLEMS. The status block above says all fourteen generators are `ok`. Thirteen of
them are. The fourteenth is a stub, and the block cannot tell you that.

(1) table_3_4_gpu_speedups IS NOT MEASURED IN THIS ARCHIVE, DESPITE SAYING `ok`.

Its CSV holds four rows reading `(not run: GPU arm unavailable)` / `N/A`, against
thirty-two measured rows in `uniform-2026-08-03`. What happened is in
`logs/table_3_4_gpu_speedups.log`: the generator ran and measured nearly everything --
Boruvka MST, the VAT front end, Fuzzy C-Means at all three sizes with both CPU arms
(500,000: 39.71x unmatched, 3.91x matched), and the float64 pairwise sweep. Then its
worker processes were killed by the author. The orchestrator caught that and took its
`--- retrying without the optional GPU dependency ---` path, which re-ran the generator
in an environment with no CuPy, detected no device, emitted the four N/A rows with the
reason, OVERWROTE the good CSV and MD, and exited 0. Exit 0 is why the status says `ok`.

That is a harness defect independent of the kill that triggered it. A retry intended to
tolerate a missing optional dependency should not be able to clobber a successful
primary result, and `ok` should distinguish "measured" from "emitted N/A because
blocked". Any transient fault in the GPU path would silently downgrade this table and
report success. Filed against the harness; the numbers survive in the log either way.

(2) THE GENERATORS WERE UNCOMMITTED WHEN THIS RUN STARTED.

Four had been switched to leak-free preprocessing and not yet committed:
table_concrete_reconciliation.py, table_hyperparam_normalization.py,
table_g5_output_partitioning.py, table_g5b_skew_sweep.py. So the grad-school SHA in the
header, b22c6a7, does not contain the code that produced these numbers. The commit that
adds this addendum contains it.
