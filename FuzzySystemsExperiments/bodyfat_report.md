# Body fat % from body measurements (`TribbleRegressor`)

Penrose/Johnson body-fat data: 252 men, `BodyFat` predicted from anthropometric measurements. Generated by `FuzzySystemsExperiments/bodyfat.py`.

## `Density` is the answer, not a feature

The `BodyFat` column was computed from `Density` by Siri's equation, %BF = 495/D - 450. Reconstructing it that way reproduces the column to **RMSE 1.260 percentage points** over all 252 rows -- so `Density` is not a predictor of the target, it *is* the target in another coordinate. It is excluded from every model below; the remaining 13 features are what a tape measure and a scale give you.

The same check surfaces 5 rows the equation does *not* reproduce -- the dataset's known transcription errors. They are left in the data (reported, not repaired):

| 75.000 | 1.067 | 18.500 | 14.092 | 4.408 |

**Read the baselines first.**

- Predicting the training mean gives RMSE 8.37. That is the floor.
- `Abdomen` alone -- one tape measurement -- gives **4.92**. This is the number that matters: any model that does not beat one circumference is not earning its complexity.
- OLS on all 13 features gives **4.49**, and it is the best model here.

`TribbleRegressor` out of the box gives 7.02 -- worse than one tape measurement, and barely better than the mean. Capping its capacity and scaling its inputs properly (`TribbleRegressor (log-tuned), Abdomen+Hip+Chest`) brings it to **4.82 ± 0.21**: past the one-circumference baseline (4.92), level with OLS on the same three features (4.71), still behind OLS on all 13 (4.49).

### Scaling, and the log transform

Scaling is the single biggest lever found on this dataset, and it needs three facts stated before the numbers mean anything.

**The default estimator is invariant to affine rescaling.** Raw features, sklearn `StandardScaler`, `tribblefis` `MinMaxScaler` and `tribblefis` `StandardScaler` all give a byte-identical RMSE of 7.021 for the default config. Per-feature Gaussian membership fitting and least-squares consequents are both unchanged by a per-feature affine map, so min-max versus z-score cannot matter on its own. (`tribblefis.scaling` warns that z-scoring is actively harmful to fuzzy models; that finding is documented for a pipeline with output bucket means pinned to `[0,1]` and a scaled target, neither of which is in play here — so it does not apply, and is not contradicted.)

**Only a nonlinear transform moves the model**, which makes the log the real lever. Affine scaling does still matter *indirectly* for the tuned configs, because `top_n` feature selection and `l2_reg` are not scale-free: the same `l2_reg=1.0` that suits z-scored features is a crushing penalty on `[0,1]`-bounded ones (5.09 → 5.70). Configs therefore have to be re-swept under whatever scaling they will run in, which is what the `log-tuned` row is.

**Automatic log detection never fires here.** It triggers at `log_dynamic_range=3.0` decades and the widest feature spans 0.57:

| feature | decades |
|---|---|
| Age | 0.566 |
| Weight | 0.486 |
| Height | 0.421 |
| Abdomen | 0.329 |
| Thigh | 0.267 |
| Biceps | 0.259 |
| Ankle | 0.249 |
| Hip | 0.240 |
| Chest | 0.235 |
| Forearm | 0.221 |
| Neck | 0.217 |
| Knee | 0.173 |
| Wrist | 0.132 |

So `MinMaxScaler()` and `MinMaxScaler(log_dynamic_range=None)` are identical on this data, and the log has to be named explicitly with `log_features`. With it named, the fuzzy model reaches its best result here — and the transform *hurts* OLS (4.71 → 5.36 on the trio) while helping the fuzzy system (5.05 → 4.82). The relationship really is closer to linear in raw units; the log buys a better rule partition without buying a better regression line.

### The `Abdomen+Hip+Chest` subset

Three circumferences -- the measurements a clinician would actually take, and a far better match for this estimator's capacity than thirteen features. It does not rescue it. OLS on those three alone gives **4.71**; the best fuzzy model on the same three gives **5.07**. Note where the two families end up: the fuzzy system scores about the same on three features as on thirteen (5.07 vs 4.82), while OLS keeps improving as features are added (4.71 -> 4.49). Extra measurements carry linear information this TSK configuration does not convert into accuracy.

That tuned figure is also a worked example of why the repeat over fold partitions is here: on seed 0's folds alone -- the partition the 288-point grid search picked the config on -- it scored 4.85, and across all 5 partitions it is 4.82. The 0.2 pp difference is selection bias, not noise, and quoting the 4.85 would have been quoting the search's own choice back at itself.

The `starved-rule warnings` column is the estimator's own complaint that some output buckets were fitted on almost no data (0 such warnings for the tuned config): part of what looks like a working 4-rule model is rules with nearly nothing behind them.

**The honest conclusion.** With the right scaler the fuzzy model draws level with OLS on the same three features -- 4.82 against 4.71, a gap inside its own ±0.21 spread -- but still loses to OLS on all 13 (4.49), and never beats it anywhere. Body fat is close to linear in these circumferences, so the linear model is hard to beat on its own ground; what the log transform buys the fuzzy system is a rule partition good enough to match it, not to overtake it. The honest reading is a draw at three features and a loss at thirteen -- which is a better result than the first pass suggested, and it took the library's own scaler to get there.
