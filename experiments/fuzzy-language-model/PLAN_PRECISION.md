# PLAN_PRECISION: lower-precision training, and checkpoint / resume with Weights & Biases, before scaling (registered 2026-10-23)

Owner's request: before scaling up, explore BF16 or another more efficient floating-point setup, and support checkpoint and resume, specifically with Weights & Biases.

## What was true before this plan
Training was **plain FP32 everywhere**: no autocast, no bf16, no TF32 matrix mode, no `torch.compile` (grep of `flm/` found none of them). It had not been considered. A CUDA-graph attempt on the 100K model (`CHECKLIST_NEXTROUND.md` A1) gave 1.01x, so kernel-launch overhead was not that model's bottleneck. At 14M the matrix work is larger and lower precision has more to give.

## What was built (tested on the CPU; the GPU was busy)
- `flm/ckpt.py` and new flags in `flm/train.py`, all off by default (the default run is the same computation as before; the logits are cast to float, which is a no-op in fp32):
  - `--precision fp32|tf32|bf16|fp16`: tf32 enables TF32 matrix multiplies (Ampere or newer); bf16 and fp16 run the forward pass and loss under autocast (fp16 with a gradient scaler), with the optimiser, weights and master copies in fp32. Validation inside the run uses the training precision; the result file also carries `val_bpc_fp32`, the final model re-scored in fp32, which is the metric of record. `peak_mem_mb` is now recorded.
  - `--ckpt-dir`, `--ckpt-every`, `--ckpt-keep`, `--resume auto|<file|dir>|wandb:<entity>/<project>/<artifact>:latest`: a checkpoint holds the model, the optimiser moments, the next step, the numpy generator that draws batches, the torch and CUDA generators, the EMA copy, the loss-scaler, the curves and the training seconds; it is written atomically and the newest `--ckpt-keep` are kept. A resume **refuses to start if the arguments differ** from those of the run that wrote the checkpoint.
  - `--wandb <project>`, `--wandb-name`, `--wandb-artifacts`: loss, learning rate and validation curve to Weights & Biases; the run id is stored in the checkpoint so a resumed run continues the same W&B run; artifacts are optional.
- `test_resume.py` (6 tests, 60 s): a run resumed from its step-20 checkpoint ends **bit-identical** to an uninterrupted run (evaluations, final value, training curve); a resume with a changed learning rate is refused; checkpoint pruning and atomic writes; bf16 autocast runs and is re-scored in fp32; the W&B hook logs, uploads artifacts, finishes, and a resumed run reuses the same W&B id (tested with a stand-in module).
- Not done: the `wandb` package is **not installed** here (installing needs the owner's yes), no real W&B run has happened, and the real service path (`wandb.init`, `wandb:` artifact download) is untested. An API key is the owner's to provide (`wandb login` or `WANDB_API_KEY`); the code never touches credentials. The `--resume wandb:...` download path is the part most likely to need a fix on first use.

## The precision screen (queued behind the 14M upper-lr screen; one job at a time)
14M model, 30M characters, lr 1e-2, warm-up 600, seed 0 (one seed: differences under about 0.005 are noise): `fp32` (a rerun, which must reproduce 0.94487 from the earlier run: the manipulation check that the new code did not change the default path), `tf32`, `bf16`, `fp16`. Then the 100K model F7, 30M characters, seeds 0-2, `fp32` against `bf16`. Measured: bits per character (autocast and fp32 re-score), tokens per second, peak memory. A T4 has no bf16 or TF32, so fp16 is the arm that matters for Colab; the 4080 can run it for numerics but not for T4 speed.
Predictions: the fp32 rerun reproduces 0.94487 exactly (85%); bf16 trains the 14M model at least 1.3x faster than fp32 (55%); tf32 at least 1.3x (50%); fp16 at least 1.3x (50%); bf16's fp32 re-score is within 0.01 of fp32 (65%); fp16 diverges or loses at least 0.02 without further fixes (35%); F7 (100K) gains under 1.15x from bf16 (70%, launch-bound); bf16 costs F7 at least 0.02 (30%, the recurrent mixer state may need fp32); peak memory drops by at least 25% under bf16 (60%).
Decision rule: a precision mode becomes the default for the 14M-and-up work only if its fp32 re-score is within 0.005 of fp32 on the 14M model and it is at least 1.3x faster; the 100K recipe stays fp32 unless F7 gains at least 1.15x at no more than 0.003 cost, five seeds. Whatever is chosen is confirmed in one 300M run before it is used for anything quoted.
